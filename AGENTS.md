# AI Instructions for ld-decode

---

## 1. Overview & Core Constraints

### 1.1 Role & Scope
- You are a coding assistant for the **ld-decode** project.
- For pull-request workflows, see the PR template in `.github/PULL_REQUEST_TEMPLATE.md`.

**ld-decode** is a software-defined decoder for LaserDisc RF captures. It demodulates raw RF samples
(`.lds`, `.ldf`, `.s16`, `.u8`, `.r30`, …) into time-base-corrected video (`.tbc`), spec-compliant
composite video (`.cvbs`/`.meta`), analogue audio (`.pcm`), digital audio (`.efm`) and metadata.

- **Type:** Python 3 signal-processing application (NumPy / SciPy / Numba)
- **Package:** `lddecode/` — importable library plus CLI entry points
- **Build & test driver:** CMake 3.16+ / CTest (wraps the Python tools); packaging via `pyproject.toml`
- **Reproducible builds:** Nix (authoritative) with `flake.nix`
- **Target platforms:** Linux (AppImage), macOS (DMG), Windows (ZIP)

### 1.2 Git Operations
- **Do not** run `git add`, `git commit`, `git push`, `git stash`, or any command that modifies
  repository state unless the user explicitly requests it.
- Read-only commands (`git status`, `git log`, `git diff`, `git show`) are permitted.
- **Never** run `git submodule update`, `git submodule deinit`, or anything that rewrites the
  submodule checkouts (`testdata/`, `analogue-video-specifications/`,
  `cvbs-file-format-specification/`) unless explicitly asked.

### 1.3 Naming
- Never use planning-phase terminology (e.g., `phase0`, `rev8_new`, `mvp-phase`).
- Use **descriptive, domain-oriented names**: `sync_detect`, `burst_level`, `field_anchor`,
  `lattice_positions`, `demod_block_cache`.
- Module, function and variable names follow PEP 8 (`snake_case`); classes are `CapWords`.

### 1.4 Content Restrictions
- Do **not** include advertisements, promotions, or commercial references.
- Omit "generated by", "co-authored by", or tool/service attributions.

## 2. Architecture & Module Boundaries

`lddecode/` is layered by import direction. Do not create cycles; a module may only import from
layers **below** it.

| Layer | Modules | May import from |
|-------|---------|-----------------|
| 0 — primitives | `dsp`, `fft8`, `fdls`, `efm_pll`, `ac3rf`, `commpy_filters`, `profiling`, `utils_logging`, `utils_plotting`, `lds`, `ldf_reader` | stdlib / third-party only |
| 1 — parameters & I/O | `filters`, `params`, `fileio`, `cvbs`, `cx` | layer 0 |
| 2 — measurement | `pulses`, `metrics`, `audio`, `parallel` | layers 0–1 |
| 3 — demodulation & fields | `rfdecode`, `field` | layers 0–2 |
| 4 — orchestration | `decoder` (`LDdecode`) | layers 0–3 |
| 5 — entry points & facades | `main`, `cut`, `compress`, `start_finder`, `core`, `utils` | layers 0–4 |

Rules:
- `core.py` and `utils.py` are **re-export facades only** — no logic lives in them. New code imports
  the specific module (`from .field import Field`), not `from lddecode.core import *`.
- Layer 0–3 modules must **never** import `decoder`, `main`, or any CLI module.
- Layer 0 modules must have no intra-package imports at all; they are the units that are easiest to
  unit test, so push pure computation down into them.
- No module below layer 5 may call `sys.exit()`, parse `argparse` arguments, or print to stdout.
  Report through `logging` (via `utils_logging`) and raise exceptions instead.
- `analysis/` and `scripts/` are consumers of `lddecode`; nothing inside `lddecode/` may import them.

**Adding new features:**
1. **Computation:** put the pure, side-effect-free maths in the lowest layer it fits (usually
   `dsp`, `filters`, `params`, or a new leaf module); add unit tests under `tests/unit/`.
2. **Wiring:** connect it in `field`/`rfdecode`/`decoder` with the dependency passed in, not
   constructed inline, so tests can substitute it.
3. **Interface:** add CLI flags in `main.py`/`cut.py` only; keep the library callable without them.
4. **Verification:** add a functional test (CTest) only when the behaviour genuinely needs real RF
   data or a full decode run.

## 3. Security

- **Never** hard-code secrets, tokens, credentials, or API keys in source, configs, or logs.
- Use environment variables or a dedicated secrets manager for sensitive data.
- Validate and sanitise all external inputs (file paths, CLI arguments, metadata JSON, frame counts
  and sample offsets read from capture files).
- Never build a shell command by string concatenation from user input — use `subprocess` with an
  argument list and `shell=False`.
- Never `eval`/`exec` input, and never `pickle.load` data that did not come from this project.
- Treat capture files as untrusted: bounds-check every length, offset and count taken from a file
  header before it is used to size an allocation or index an array.
- Report suspected security issues **privately** via GitHub Security Advisories.

## 4. Testing & Quality Assurance

### 4.1 General Rules
- Source of truth: `TESTING.md`.
- Unit tests are the **primary** methodology; prefer them for all new or modified behaviour.
- Requirements:
  - Mock or inject dependencies; tests must be **deterministic**.
  - No filesystem, network, system clock, subprocess, or external-service dependencies.
  - Seed every generator explicitly (`np.random.default_rng(12345)`); never use unseeded randomness.
  - Keep tests isolated and fast (each unit test well under 100 ms).
  - Use dependency injection: pass callables/objects into constructors rather than importing and
    constructing them inside the unit under test.
  - Name tests by behaviour (e.g., `test_pal_lattice_slips_four_samples_per_frame`).
- Classification:
  - **Every** new or modified test must be marked as **either** `unit` **or** `functional` — with a
    `pytest.mark` and, where it is registered with CTest, a matching CTest label.
  - Use `functional` **only** when the objective cannot be met with a unit test.
  - Tests touching the filesystem, the `testdata/` submodule, subprocesses, or a full decode run
    **must** be `functional`.
- CI: the default unit lane must stay fast and hermetic; do **not** add functional tests to it.

### 4.2 Unit Test Constraints (Non-Negotiable)

**Unit tests MUST NOT access the filesystem, network, subprocesses, or the system clock under ANY
circumstances.** This is enforced in code review:

- ❌ **Forbidden:** `tmp_path`, `open()`, reading a `.ldf`/`.tbc`/`.json` fixture, `subprocess.run`,
  `requests`, `time.time()` used as an input, unseeded `np.random`
- ❌ **Forbidden:** calling code that touches disk "just to test the happy path"
- ❌ **Forbidden:** importing `lddecode.core` to reach a symbol — import the owning module directly
- ✅ **Required:** feed synthetic NumPy arrays constructed in the test, or `io.BytesIO` for
  byte-stream logic
- ✅ **Required:** substitute collaborators with `unittest.mock.Mock`/`monkeypatch` and assert on the
  calls made to them, not on their behaviour
- ✅ **Required:** test the unit's logic in isolation, with tolerances stated explicitly
  (`np.testing.assert_allclose(..., rtol=…, atol=…)`) rather than relying on exact float equality

**Example:** to test `.lds` 10-bit packing, do not write a file and shell out to a converter — build
the sample array in the test, run it through `pack`/`unpack` in memory, and assert bit-exactness.
To test block-cache scheduling, inject synthetic `read_fn`/`demod_fn` closures (see
`tests/test_parallel_blockcache.py`) instead of running a real demodulation.

See the "Unit tests" section of `TESTING.md`, and `tests/test_cvbs_lattice.py` and
`tests/test_parallel_blockcache.py` as reference structure.

**When adding/changing behavior:**
1. Write or update unit tests first.
2. Inject or mock external dependencies (file I/O, subprocesses, threads, wall-clock).
3. Run the label-appropriate invocation from `TESTING.md` locally.
4. Confirm no layer-boundary violation was introduced (§2).

### 4.3 Test Labels

Use pytest markers locally and CTest labels for the CMake-driven lanes; keep the two aligned.

| Label | Scope |
|-------|-------|
| `unit` | Fast, hermetic pytest suites under `tests/unit/` |
| `functional` | Tests requiring real capture data, subprocesses, or a full decode |
| `dsp` | Filter, demodulation and signal-maths unit tests |
| `format` | File-format unit tests (`.lds`, `.ldf`, `.cvbs`, `.tbc`, metadata) |
| `decode` | Field/frame assembly, sync and TBC logic unit tests |
| `parallel` | Threading, block-cache and speculation unit tests |
| `slow` | Functional tests that exceed roughly 60 s |

### 4.4 Decoder Expectations

For new decode behaviour and changes to existing decode behaviour:
- Add the matching unit suite under `tests/unit/` naming the module under test
  (`tests/unit/test_<module>_<behaviour>.py`) in the same PR.
- Preserve the serial/threaded equivalence guarantee: a `-t N` decode must remain **bit-identical**
  to the serial decode with `--exact-speculation`. Any change to `parallel.py`, `decoder.py`, or
  cached demodulation must keep the `compare-*-parallel-*` CTest comparisons passing.
- Preserve format conformance: `.cvbs` output must continue to satisfy `analysis/cvbs_verify.py`
  against `cvbs-file-format-specification/`.
- Update the relevant page under `docs/` in the same PR whenever a CLI flag, output file, or
  metadata field changes (see §10).

### 4.5 Analysis & Tooling Expectations

`analysis/` scripts are test oracles, not scratch code. When changing one:
- Keep its `PASS`/`FAIL` output line stable — CTest matches it with `PASS_REGULAR_EXPRESSION`.
- Keep the skip path intact for optional external tools (e.g. `ORC ROUNDTRIP: SKIPPED` when
  `orc-cli` is absent); never make a previously optional dependency mandatory.
- Put reusable measurement maths in `analysis/video_common.py` (or `lddecode/metrics.py` when the
  decoder needs it too) and unit test it there.

### 4.6 Validation Gates

Run the narrowest set that matches the change scope before proposing changes.

Library or analysis changes (no decode behaviour):
1. `nix develop --command python -m pytest -q tests/unit`
2. `nix develop --command python -m pytest -q tests` (whole suite, if quick enough)

Decode behaviour changes:
1. `nix develop --command cmake -S . -B build -DCMAKE_BUILD_TYPE=Release`
2. `nix develop --command ctest --test-dir build -L unit --output-on-failure`
3. `nix develop --command ctest --test-dir build -L functional --output-on-failure`

Threading, caching or speculation changes — additionally confirm serial/threaded bit-identity:
- `nix develop --command ctest --test-dir build -R "parallel" --output-on-failure`

Functional lanes need the `testdata/` submodule checked out. If it is missing, say so rather than
skipping the gate silently.

## 5. Python Coding Standards

### 5.1 Baseline & Tooling
- Follow [PEP 8](https://peps.python.org/pep-0008/) as formatted by **black** (`line-length = 100`,
  configured in `pyproject.toml`); import order follows **isort** (`profile = "black"`).
- Type hints on new public functions; `mypy` settings live in `pyproject.toml`. Do not add
  `# type: ignore` without a comment saying why.
- **Never** hand-align columns (extra spaces before `=`, aligning continuation lines to an opening
  parenthesis) — black will undo them.
- Do not reformat files you did not otherwise change; keep diffs reviewable.
- The package supports the Python version pinned by `flake.nix` (currently 3.12); avoid syntax newer
  than the `requires-python` floor in `pyproject.toml` in library code.

### 5.2 Module Headers
- Every module starts with a docstring; every **new** module and every CLI entry point carries an
  SPDX header inside that docstring, above all other content.
- Template (matching `lddecode/lds.py`):
  ```python
  """
  sync_detect - horizontal and vertical sync location for LaserDisc fields

  SPDX-License-Identifier: GPL-3.0-or-later
  SPDX-FileCopyrightText: 2026 ld-decode contributors

  Locates sync pulses in demodulated video and reports their sub-sample
  positions; consumed by field.py when building a field's line map.
  """
  ```
- The first line names the module (matching the filename) and its purpose in one phrase.
- The prose below states what the module does and who consumes it.
- Executable entry points keep the `#!/usr/bin/env python3` shebang **above** the docstring.

### 5.3 Custom Additions

#### 5.3.1 Interfaces & Dependency Injection
- ld-decode uses duck typing rather than formal interfaces; make the expected protocol explicit in
  the docstring, or declare a `typing.Protocol` for anything a test will substitute.
- Pass collaborators (loaders, writers, thread pools, clocks) into the constructor or call; do not
  construct them inside the unit that uses them.
- Anything that opens a file, spawns a process, or starts a thread must be reachable through an
  injected seam so unit tests never need it.

#### 5.3.2 NumPy & Memory Safety
- Be explicit about dtypes (`np.int16`, `np.float64`); never rely on platform-default integer width.
- State whether a function returns a **view** or a **copy**, and never mutate an array passed in
  unless the docstring says it is an in-place operation.
- Prefer vectorised NumPy over Python loops; where a loop is unavoidable and hot, use
  `@njit(nogil=True, cache=True)` and keep the body to Numba-supported constructs.
- Bounds-check every index derived from file contents or measured signal positions.
- Do not silently clip or wrap: raise, or return an explicit sentinel the caller must handle.

#### 5.3.3 Concurrency
- Document thread-safety for every public class or function that can be reached from a worker.
- Threading rules for the decode pipeline: all raw reads go through the single reader lock; cached
  demodulation must be a pure function of `(block index, mtf_level)` plus fixed filter state.
- Any change that can alter output must preserve serial/threaded bit-identity (§4.4).
- Prefer immutable data and message passing over shared mutable state; where state is shared, mark
  it and name the lock that guards it.

#### 5.3.4 File Organisation
- One responsibility per module; if a module exceeds roughly 1,000 lines, split it along the layers
  in §2 rather than adding to it.
- Public names go in `__all__` for modules that are re-exported.

#### 5.3.5 Constants & Clarity
- Avoid magic numbers; name them and comment the source. Video-standard constants belong in
  `params.py`.
- Use `fractions.Fraction` or integer arithmetic for lattice/timing maths — never accumulate floats
  across lines or frames.
- Reference authoritative specs when implementing standards (see §5.3.6 and §10.1).

#### 5.3.6 Specification References
- Format: `# <Organization> <Document>-<Section>: <description>`
- Examples:
  - `# ITU-R BT.1700 Annex 1 Part B Table 1 item 1 (625-line PAL).`
  - `# EBU Tech. 3280-E Section 1.2: 1135.0064 samples/line nominal`
  - `# SMPTE 170M-2004 Section 11.3: 525 lines/frame, 2:1 interlace.`
- Supported organisations: EBU, ITU-R, ITU-T, SMPTE, IEC.

#### 5.3.7 Commenting
- Docstrings state purpose, parameters, units, and return value — **units matter**: say IRE, μs,
  samples, or Hz explicitly.
- Explain the approach above a complex algorithm; document the rationale behind non-obvious
  decisions, especially empirical constants and tolerances.
- Use `# TODO: <description>`; avoid redundant comments that restate the code.

## 6. Performance

- **Profile before optimising** (`scripts/bench_rf.py`, `lddecode/profiling.py`, `cProfile`); prefer
  measurable gains over premature micro-optimisation.
- Minimise copies: prefer in-place NumPy operations and views where ownership allows, and avoid
  materialising a whole capture in memory.
- Document Big-O complexity for public algorithms; note per-field and per-block allocation costs.
- Flag any change that increases memory use by >10 % or decode time by >5 % for design review.
- Numba: keep `@njit` functions monomorphic and `cache=True` where the signature is stable;
  remember first-call compilation cost when timing.
- Prefer FFT-domain filtering for long kernels, and keep block sizes powers of two where the
  pipeline already assumes them.

## 7. Development Environment & Build

- The project uses **Nix**; the provided development shell is authoritative.
- Run normal workflows inside the project shell:
  `nix develop "path:$PWD" --command <command>`
- Temporary tools (profiling, debugging, one-off analysis):
  - Use ad-hoc shells:
    `nix shell nixpkgs#<tool> --command <tool> <args>`
    `nix shell nixpkgs#<tool1> nixpkgs#<tool2> --command <command>`
- Do **not** modify `flake.nix` solely for temporary dependencies, and do **not** `pip install` into
  the Nix shell.
- Always provide the Nix-based equivalent alongside plain shell commands.

**Nix-based workflow (recommended):**
- `flake.nix` defines the Python interpreter, all Python dependencies (`av`, `matplotlib`, `numba`,
  `numpy`, `scipy`, `pytest`, `pytest-cov`, `jupyter`, `pandas`), the docs toolchain, and the
  runtime tools the CLI shells out to (`ffmpeg`, `flac`).
- `nix develop` gives you everything; nothing needs to be installed on the host.
- When already inside `nix develop` and a one-off extra tool is needed, prefer `nix shell` to pull it
  in rather than installing it on the host or assuming it exists.

**Submodules:**
- `testdata/` — CI capture data; required by the functional lane.
- `analogue-video-specifications/`, `cvbs-file-format-specification/` — normative references (§10.1).
- Clone with `git clone --recurse-submodules`; never rewrite a submodule checkout unprompted (§1.2).

**Non-Nix workflow:**
- `pip install -e ".[dev]"` in a virtualenv works for pure-Python iteration, but the Nix shell is the
  reference environment and the one CI uses. Reproduce a failure under Nix before reporting it.

**Quick flow (Nix-based, recommended):**

```bash
# Enter the reproducible development environment
nix develop

# Fast, hermetic unit tests
python -m pytest -q tests/unit

# Configure CTest (also regenerates lddecode/version)
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release

# Full suite, including functional decode tests
ctest --test-dir build --output-on-failure
```

**Key points:**
- `cmake` configuration writes `lddecode/version` from git; the CLI `--version` output comes from it.
- `nix build` produces `./result`; `nix run .#ld-decode` runs the packaged CLI.
- `nix build .#docs` builds the MkDocs site; `mkdocs serve` previews it from the dev shell.

For complete build instructions see [BUILD.md](BUILD.md); for installation see [INSTALL.md](INSTALL.md).

## 9. Output Formats & Downstream Contracts

ld-decode's outputs are consumed by other tools; their formats are contracts, not implementation
details.

- `.tbc` + `.tbc.json` — time-base-corrected video and its metadata, consumed by the legacy
  ld-decode-tools chain and decode-orc.
- `.cvbs` + `.meta` — composite video, normatively defined by `cvbs-file-format-specification/`.
- `.pcm`, `.efm`, `.ac3` — analogue audio, EFM, and AC-3 RF side outputs.

Rules:
- **Never** change a field's meaning, units, or position in an existing output without saying so
  explicitly and updating the format documentation in the same PR.
- Adding an optional metadata field is acceptable; removing or repurposing one is a breaking change
  and requires the user's agreement (§17).
- When code and specification disagree, the specification wins: fix the code **and** the tests
  (§10.1).
- `analysis/cvbs_verify.py` is the executable statement of `.cvbs` conformance. If a change makes it
  fail, either the change or the verifier is wrong — do not relax the verifier to make a decode pass.

**Documentation that must be kept in sync:**

| Change | Doc to update |
|--------|---------------|
| CLI flag added, removed, renamed, or default changed | `docs/user-guide/command.md` |
| New or changed output file type | `docs/technical/file-formats.md` |
| `.tbc.json` metadata field added, removed, or repurposed | `docs/technical/metadata-format.md` |
| Filter or servo tuning parameter added or changed | `docs/technical/filter-tuning-parameters.md` |
| VITS-driven servo behaviour changed | `docs/technical/vits-servos.md` |
| Helper script added or behaviour changed | `docs/user-guide/scripts.md` |
| Build, install, or dependency change | `BUILD.md` / `INSTALL.md` |

## 11. CI/CD & Multi-Platform

Current workflows (`.github/workflows/`):

- **build-and-test.yml:** primary gate. Runs on Linux with Nix; configures CMake and runs `ctest`,
  then fans out to the packaging workflows.
- **functional-tests.yml:** the same functional lane, on manual dispatch.
- **appimage.yml:** builds the Linux AppImage.
- **macos-dmg.yml:** builds the macOS DMG.
- **windows-zip.yml:** builds the Windows ZIP.
- **deploy-docs.yml:** publishes the MkDocs site.

**Before proposing changes:**
- Test locally with the Nix/Linux flow (primary CI gate).
- CI checks out submodules recursively; a test that needs data must use `testdata/`, not a file the
  runner does not have.
- If modifying packaging or dependencies, review the platform-specific workflow for that target.
- Document in the PR what was validated locally and what could not be (e.g., "Unable to validate the

## 13. Contribution Hygiene

- **Focused changes:** one clear problem per PR.
- **Commit messages:** clear, descriptive; reference issue numbers.
- **Documentation:** update `docs/`, `README.md`, `BUILD.md`, or `INSTALL.md` when behaviour or usage
  changes (see §9).
- **Avoid refactoring unrelated code** — and never let a formatter rewrite files the change did not
  touch.
- **Do not commit** capture data, decode outputs, `build/`, `__pycache__/`, or notebook output cells.
- **Search existing issues and PRs first** to avoid duplicates.

---

## 14. Implementation Planning

- Plan documents live in `plans/`.
- Structure plan documents as **phased** tasks for agentic coding.
- Requirements:
  - ≤ 10 tasks per phase (ideally 3&ndash;5).
  - Clear descriptions and acceptance criteria per task.
  - No decorative sections (TOC, summaries).
  - No timelines or resource estimates.
  - Each phase must be self-contained and actionable.
  - Link directly to referenced specs, designs, or sources.
  - Follow testing rules from `TESTING.md` and §4.
- Change history belongs in git; do **not** include it in plan files.

## 15. Guardrails

- **Trust the instructions:** use them as the source of truth. Search the codebase only if the
  instructions are incomplete or found to be incorrect.
- **Verify build commands:** if docs disagree with the CI workflows, the workflows are correct; flag
  the discrepancy in your PR.
- **Respect the layering:** the import direction in §2 is not negotiable.
- **Signal correctness over convenience:** never widen a tolerance, relax a verifier, or delete an
  assertion to make a test pass. Find the cause.
- **Test first, refactor never:** don't introduce new frameworks or patterns unless explicitly
  requested; follow existing conventions.

---

## 16. Communication Style

- Be concise; prefer bullet lists and fenced code blocks over prose.
- Explain non-obvious choices or trade-offs in one short sentence.
- Cite authoritative specs, files, or line numbers when referencing requirements.
- State measurement units (IRE, μs, samples, Hz) whenever you quote a number.
- Use markdown headers and separators to structure long responses.

---

## 17. Clarification Triggers

Ask the user when:
- Requirements are ambiguous or contradictory.
- A change affects a CLI interface, an output file format, or backwards compatibility.
- A change would alter decoded output for existing captures.
- Multiple valid approaches exist with significantly different trade-offs.
- A task may have security, licensing, or performance implications.

## 18. Common Commands Reference

```bash
# Enter the reproducible environment (everything below assumes this, or prefix with
# `nix develop --command`)
nix develop

# Fast hermetic unit tests
python -m pytest -q tests/unit

# One test file, verbose
python -m pytest -v tests/unit/test_cvbs_lattice.py

# One test by name
python -m pytest -q -k "pal_lattice"

# Unit tests with coverage
python -m pytest -q --cov=lddecode --cov-report=term-missing tests/unit

# Configure CTest (also regenerates lddecode/version)
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release

# Fast lane only
ctest --test-dir build -L unit --output-on-failure

# Functional lane only (needs the testdata submodule)
ctest --test-dir build -L functional --output-on-failure

# Everything (matches the CI expectation)
ctest --test-dir build --output-on-failure

# One functional test by name
ctest --test-dir build -R decode-ntsc-cvbs --output-on-failure

# Serial/threaded bit-identity checks
ctest --test-dir build -R "parallel" --output-on-failure

# Format and lint before proposing changes
black lddecode tests analysis scripts
isort lddecode tests analysis scripts

# Build the package and the docs
nix build
nix build .#docs
```
